Android Chat Coach

A pixel-faithful Android plan based on the current iOS implementation, with a deliberate split between fully local coaching through Gemini Nano and the richer Emotica server path.

Status: planning only — no code changed  ·  Audience: Android, backend, product, privacy, analytics  ·  Scope: text coach first; voice remains a later layer

RecommendationPort the behavior contract before porting the visual shell. Android should select a privacy route first, assemble a bounded context second, generate a structured response third, and render the same cards and controls as iOS. Gemini Nano must never silently become a cloud request after the user selects fully on-device mode.

Audit rating and corrections

Plan rating: 8.5/10 for architecture; 7/10 for ship readiness before this revision. The first draft correctly mapped the iOS pipeline and privacy routes, but it needed sharper Android decisions: the cloud provider key must never be a long-term Android client dependency, Gemini Nano structured output must be treated as capability-dependent, local retrieval should start deterministic before adding an embedding model, and the rollout must separate parity work from Nano experimentation.

1. Audit: what iOS actually does today

The implementation is centered in emotica-ios/Emotica/CoachChatView.swift and supported by OnDeviceLLMManager, OnDeviceRAGManager, OnDeviceToolRouter, CoachSafetyScanner, CoachPersonaStore, CoachQuotaManager, SwiftData chat models, Supabase/MCP services, and Analytics feature flags.

Conversation state

SwiftData stores sessions and messages. A session has a title, insight context, timestamps and a summary/learned facts layer. The active on-device model session is reset when a conversation changes and reused across turns.

Personal context

Each send combines the latest entries, Mental Sky entries, local trend calculations, relevant semantic memories, profile/about-me, goals, response length, coaching style, language, recurring trigger focus and the selected persona.

Privacy routing

standard uses local context plus the cloud coach. enhanced sends no journal context. ondevice uses local RAG and Foundation Models when available; unavailable devices use a separate hybrid fallback with an honest disclosure.

Safety and quality

Input is scanned locally. Crisis handling has a deterministic resource card and local fallback text. Cloud replies pass a quality gate. On-device replies are not sent to cloud for correction because that would violate the privacy choice.

iOS request lifecycle

flowchart TD A[User sends message] --> B[Consume cloud quota only if cloud may be used] B --> C[Persist user bubble] C --> D[Local safety scan] D --> E{Privacy mode} E -->|enhanced| F[No journal context] E -->|standard| G[Local semantic match + recent mood summary] E -->|ondevice| H[Local RAG: embed query, cosine search, bounded context] F --> I[Build system prompt] G --> I H --> I I --> J{Nano/Foundation Models available?} J -->|yes and ondevice| K[Persistent structured session + routed tools] J -->|no and ondevice| L[Cloud response with explicit hybrid disclosure] J -->|cloud mode| M[Groq → Gemini fallback, optional MCP reads] K --> N[Validate structured fields] L --> N M --> N N --> O[Parse actions, replies, impacts, discovery prompts] O --> P[Render message + cards] P --> Q[Persist assistant bubble, source and feedback]

What the iOS on-device session contains

  • A compact system prompt with style, strict language, user facts, current date, response length and recurring-focus guidance.
  • A persistent transcript for the current chat; the transcript is carried when the tool set changes.
  • Structured output: message, quickReplies, discoveryQuestions and impactLabels.
  • Tools selected by the user message: journal search, recent moods, emotional patterns, calendar event, reminder, notification, journal creation and journal update.
  • Context budgeting against a 4,096-token model window. Memories receive priority, recent moods fill remaining space, and every user-supplied prompt field is sanitized and capped.

Tablet and foldable support plan

Tablet readiness rating: 5/10 today. The Compose screens are reusable, but the navigation is phone-first: the app uses a bottom navigation shell, many views stretch with fillMaxWidth(), and only onboarding has a deliberate max-width. We should add adaptive layout rules at the navigation and content boundaries rather than copy every screen into a tablet version.
flowchart LR W[WindowSizeClass + posture] --> N{Width} N -->|compact <600dp| P[Phone: bottom navigation + one pane] N -->|medium 600–839dp| M[Large phone/small tablet: navigation rail + one pane] N -->|expanded ≥840dp| T[Tablet: rail + list/detail or two-pane] T --> C[Shared ViewModels and repositories] M --> C P --> C C --> R[Same routes, state, analytics and privacy rules]

Adaptive rules

  • Use window size, not device labels. Read Material 3 WindowSizeClass from the current window and recompute on resize, rotation, split-screen and fold posture. Do not use isTablet, screen density, or a hard-coded model list.
  • Keep a single navigation graph. Compact windows use the current bottom bar; medium and expanded windows use a navigation rail with the same destinations. The selected destination and back stack stay in the same NavHostController.
  • Coach becomes list/detail. Expanded width shows session history in a 280–360dp left pane and the active conversation in a centered detail pane. Medium width uses a collapsible rail and one conversation pane. New chat, persona, style and privacy controls become a top-bar/action area rather than competing with the message list.
  • Bound content columns. Message bubbles, composer and settings forms use readable max widths (roughly 680–760dp) and stay centered; the background can fill the tablet. Never stretch paragraphs or chat bubbles across the entire landscape screen.
  • Use two-pane layouts for high-value screens. Mental Sky uses sky/list plus selected entry detail; Exercises uses category/filter rail plus cards; Settings uses section rail plus detail; search uses filters plus results. Logging remains a focused modal/sheet with a bounded form.
  • Preserve phone behavior. Every adaptive branch must call the same ViewModel methods and repositories. Only arrangement changes; business logic, privacy route, safety scanner, persistence and analytics do not fork.
  • Support large text and input. Respect system font scale, avoid fixed heights, use scrolling at every pane, keep a minimum 48dp touch target, and verify keyboard/pointer/keyboard navigation. Tablet screenshots must include 1.0×, 1.3× and 2.0× font scale.
  • Handle posture and resizing. On foldables, use hinge bounds/posture to avoid placing a composer or primary button across the hinge. In freeform windows, recompute layout without recreating chat state.

  2. Refactor Coach first because its session list/detail model maps directly to expanded width and is part of the current parity work.
  3. Refactor Mental Sky, Exercises and Settings using the same list/detail primitives.

First production target: standard and enhanced parity behind the server proxy. Enable on-device mode only for an internal device matrix after the Nano adapter passes privacy and safety tests. This keeps the Android release useful on every supported device while the local path matures.

4. Gemini Nano plan

Use the official ML Kit GenAI Prompt API backed by AICore, rather than embedding a model in the APK. Google documents status states of AVAILABLE, DOWNLOADABLE and UNAVAILABLE; the Prompt API requires API 26+, accepts text prompts, supports streaming and has an input limit of under 4,000 tokens. Availability is device/configuration dependent.

Privacy ruleWhen the user selects “On this device”, all journal-derived context stays local. If Nano is unavailable or fails, show a clear “On-device coach unavailable” state and offer the user an explicit one-tap switch to hybrid/cloud. Never silently send the context to the server.

Capability states

Unavailable, downloadable, downloading, ready, quota-limited, busy, safety-blocked and failed. Cache status briefly and refresh on foreground; do not query AICore from every Compose recomposition.

Session policy

One Nano session per active Room chat. Reuse it across turns. Reset on new chat, privacy change, language/persona change, or long inactivity. Serialize generation; a second send is disabled or queued.

Prompt budget

Reserve space for system instructions, response schema, tool descriptions and output. Use token counting where available; otherwise conservative character estimates. Retrieve a small top-k context and trim by record boundary.

Model limitations

Nano is a local assistant, not a clinical authority. Keep replies short, avoid diagnosis, require confirmation for writes, and use deterministic app code for calendar/reminder/journal mutations.

Official references: Gemini Nano on Android and ML Kit Prompt API setup and limits.

6. Personalisation contract

Build one platform-neutral CoachProfileSnapshot before prompting. It should contain only fields the user has supplied or the app has computed:

  • Display name, about-me, goals, response length, coaching style and effective language.
  • Selected persona ID, localized name/tagline/blurb, safe character description and custom-persona feature flag.
  • Recent emotion distribution, recurring triggers and a confidence-gated focus trigger.
  • Conversation summary and learned facts, kept per persona where iOS does so.
  • Capability and privacy mode; never place secrets, auth tokens, device identifiers or raw analytics IDs in the prompt.

Server personas should follow iOS: enabled rows from voice_personas, exact locale first, English fallback, local cache, bundled catalog fallback. Custom persona text is data, not instructions: fence, strip control delimiters, cap length, and state that safety, language and output rules override it.

7. Response contract and Android rendering

{
  "message": "Short, specific coaching response",
  "quickReplies": ["Tell me more", "Try a pause"],
  "discoveryQuestions": ["What changed today?"],
  "impactLabels": ["Calm", "Work"],
  "proposedActions": [],
  "safety": {"level": "safe", "showResources": false},
  "source": "on_device"
}

Cloud models can still return a compatibility text format during migration, but Android must parse it once at the boundary and render typed data. The UI must never show raw tags such as [[impact:...]]. Proposed calendar, reminder, notification or journal actions are preview cards; the user confirms before the app executes them. A model must never claim an action happened before the Android action layer reports success.

Message bubble

Plain text, markdown-free by default, timestamp, source/privacy label when relevant, feedback and favorite controls.

Quick replies

Two or three compact chips; tapping sends a new user turn and records that it was suggested.

Impact chips

Map canonical emotion/trigger IDs to Android localized labels and colors. Never trust arbitrary model colors or labels.

Safety card

Stable local crisis resources, emergency action, dismissible once per session, and no raw crisis text in analytics or crash logs.

8. Safety, abuse resistance and quality gates

  1. Preflight: classify locally into safe, distress, self-harm concern, imminent danger, abuse/violence, medical emergency or unknown. Do not attempt to diagnose.
  2. Route: crisis concern gets the deterministic resource card immediately; generation may add supportive words but cannot remove the resources.
  3. Prompt safety: user profile and persona fields are fenced as data; injection-like text cannot override language, privacy, safety or output rules.
  4. Postflight: reject empty, language-breaking, repetitive, incomplete or action-claiming output. Retry only within the same privacy boundary.
  5. Action confirmation: schedule/write/delete requires a preview and explicit confirmation, except a clearly stated “just log it” flow; destructive operations require a second confirmation.
  6. Fallback: local safe copy for offline/Nano errors. Cloud correction is allowed only in standard/hybrid, never in fully on-device mode.

10. Delivery sequence

Phase 0 — contract and measurement

Freeze the shared response schema, privacy matrix, event names, feature flags, localization keys and Room migration plan. Add no UI behavior yet.

Phase 1 — iOS behavior parity in Android cloud mode

Refactor Android around CoachOrchestrator; add profile/persona context, bounded context assembly, language/style rules, cloud provider fallback, typed parsing, feedback/favorites, quick replies, discovery and safe action previews.

Phase 2 — local safety and local retrieval

Port the deterministic scanner and resource copy. Add Room schema fields. Build a local index using normalized emotion/trigger/date/note features and deterministic ranking. This gives useful privacy behavior before Nano.

Phase 3 — Gemini Nano adapter

Add the ML Kit Prompt API, capability/download UI, warm-up, streaming, cancellation, quota and structured output. Gate with a remote flag and a local kill switch. Test only on supported AICore devices first.

Phase 4 — parity rendering and actions

Match iOS cards, chips, source labels, empty state, typing state, crisis card and action confirmation. Execute actions through Android repositories after confirmation; persist status.

Phase 5 — staged rollout

Internal emulator/UI tests → supported Pixel/Nano devices → 1% Android beta → 10% → 50% → 100%. Keep cloud standard mode as the default until Nano error, latency, safety and retention metrics are healthy.

11. Testing and acceptance criteria

  • Room migration preserves all existing sessions/messages and imports iOS chat exports without duplicate IDs.
  • Every privacy mode has an automated network assertion: fully on-device sends no journal text; enhanced sends no journal context.
  • Gemini Nano unavailable, downloadable, quota-limited, offline and guardrail-blocked states have deterministic UI and no crash.
  • Switching persona, language or privacy mode resets/rebuilds the local session without losing visible chat history.
  • Structured output never leaks tags, invalid labels or unsupported actions into the bubble.
  • Safety tests cover crisis language, ambiguous distress, medical questions, abuse and ordinary sadness; crisis resources remain visible.
  • Golden Compose screenshots cover light/dark themes, long languages, large font scale, RTL readiness, keyboard, rotation and fold/tablet widths.
  • Performance targets: first local response after warm-up ≤3 seconds p50, cloud p50 ≤4 seconds, no main-thread AICore status calls, and bounded memory for 1,000 journal entries.
  • Analytics dashboards separate route/source, Nano availability, fallback rate, action completion and safety interventions without collecting journal content.

12. Decisions to keep explicit

Do not promise “Gemini Nano on every Android”. AICore support and model availability vary by device, OS image, region and model download state. The product promise should be “On-device when your device supports it”, with a visible capability explanation.
  • Use server-side MCP only for standard mode and only behind the same iOS flags; do not recreate MCP inside Nano in the first release.
  • Start with Android-local deterministic retrieval. Add local embeddings only after evaluating quality, storage and multilingual coverage.
  • Keep actions app-owned and confirmation-driven. Model tool calls express intent; repositories perform the mutation.
  • Keep text coach and voice coach contracts separate. Share persona/profile/privacy primitives, not a combined streaming stack.
